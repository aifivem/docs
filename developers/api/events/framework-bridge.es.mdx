---
title: Eventos del puente de frameworks
description: Los eventos de ESX, QB / Qbox y vRP que dispara ai-core para que los scripts escritos para esos frameworks sigan funcionando, con sus argumentos exactos, y los eventos de framework a los que responde ai-core.
icon: Cable
---

ai-core se presenta como `es_extended`, `qb-core`, `qbx_core` y `vrp`, así que los scripts escritos para esos frameworks funcionan sin cambios. Parte de eso es disparar los propios eventos del framework cuando algo cambia en ai-core: carga un personaje, se mueve dinero, cambia un trabajo. Esta página lista cada evento de framework que dispara el puente, con los argumentos tal como los envía el puente, y los eventos de framework a los que responde.

**El código nuevo no debería usarlos.** Escribe contra los eventos propios de ai-core ([servidor](/es/docs/developers/api/events/server), [cliente](/es/docs/developers/api/events/client)) y la lib: llevan más información (varios trabajos, bandas, servicio) y no dependen de la forma de un framework. Esta página sirve para ejecutar y arreglar scripts existentes de ESX / QB / vRP.

<Callout type="info">
Las vistas de framework mantienen un trabajo por jugador: el trabajo en el que el jugador está de servicio; si no, su primer trabajo. ai-core en sí permite varios trabajos. ESX no tiene bandas; la cuenta `money` de ESX es el `cash` de ai-core.
</Callout>

## QBCore y Qbox: servidor

El puente los dispara en el servidor con `TriggerEvent`. Los scripts de Qbox escuchan los mismos nombres de QBCore; el puente no dispara ningún evento exclusivo de Qbox.

## QBCore y Qbox: cliente

Se disparan en el propio cliente del jugador con `TriggerEvent`.

| Evento | Cuándo | Argumentos |
| --- | --- | --- |
| `QBCore:Client:OnPlayerLoaded` | El personaje está en el mundo. | ninguno |
| `QBCore:Client:OnPlayerUnload` | El jugador volvió a la pantalla de personajes. | ninguno |
| `QBCore:Player:SetPlayerData` | Tras la carga y tras cada cambio de dinero, trabajo, banda o metadatos. | `(PlayerData: table)` el PlayerData de QB completo. |
| `QBCore:Client:OnJobUpdate` | Cambió el trabajo de framework. | `(job: table)` la tabla de trabajo de QB (como en el servidor). |
| `QBCore:Client:SetDuty` | Cambió el servicio en el mismo trabajo. | `(onDuty: boolean)` |
| `QBCore:Client:OnGangUpdate` | Cambió la banda de framework. | `(gang: table)` la tabla de banda de QB. |
| `QBCore:Client:OnMoneyChange` | Cambió el saldo de una cuenta. | `(account: string, balance: number)` el nombre de cuenta de ai-core y el nuevo saldo. |

<Tabs items={['TypeScript', 'Lua']}>
<Tab value="TypeScript">
```ts title="resource/client/index.ts"
on("QBCore:Client:OnPlayerLoaded", () => console.log("loaded"));
on("QBCore:Client:OnJobUpdate", (job: { name: string }) => console.log(`job: ${job.name}`));
on("QBCore:Client:SetDuty", (onDuty: boolean) => console.log(`on duty: ${onDuty}`));
```
</Tab>
<Tab value="Lua">
```lua title="client.lua"
AddEventHandler('QBCore:Client:OnPlayerLoaded', function() print('loaded') end)
AddEventHandler('QBCore:Client:OnJobUpdate', function(job) print(('job: %s'):format(job.name)) end)
AddEventHandler('QBCore:Client:SetDuty', function(onDuty) print(('on duty: %s'):format(tostring(onDuty))) end)
```
</Tab>
</Tabs>

<Callout type="warn">
`QBCore:Client:OnMoneyChange` lleva `(account, balance)`, el nuevo saldo, no los argumentos propios de qb-core. Un script de QB que lo lea como una cantidad ve el saldo. Prefiere `QBCore:Player:SetPlayerData` o el `onPlayerData("money", ...)` de ai-core.
</Callout>

## ESX: cliente

Se disparan en el propio cliente del jugador con `TriggerEvent`.

| Evento | Cuándo | Argumentos |
| --- | --- | --- |
| `esx:playerLoaded` | El personaje está en el mundo. | `(PlayerData: table, isNew: false)` el PlayerData de cliente de ESX. |

| `esx:setAccountMoney` | Cambió el saldo de una cuenta. | `(account: { name, money, label })`; `name` es `"money"` para el `cash` de ai-core. |

| `esx:setPlayerData` | Se ejecutó `ESX.SetPlayerData`: cambió el ped (cambio de modelo, reaparición) o cambiaron los metadatos. | `(key: string, value: any)` |

Se puso al personaje en el mundo. Se dispara 2 segundos después de que ai-core lo hiciera aparecer, como en vRP. Solo para la aparición de una carga de personaje: las reapariciones tras morir vienen del script de muerte y no lo disparan.

### vRP:playerJoinGroup and vRP:playerLeaveGroup

El personaje obtuvo o perdió un grupo de vRP. Los grupos son los trabajos de ai-core, la banda activa, los nombres de grupo que el dueño del servidor mapeó en el panel (pestaña "vRP scripts") y los grupos extra que añaden los scripts de vRP. Se dispara con cada cambio, también con los cambios que hacen ai-core u otro script sin pasar por vRP.

**Lado:** Servidor

<TypeTable
  type={{
    user_id: { type: 'number', description: 'El id del personaje.', required: true },
    group: { type: 'string', description: 'El nombre del grupo.', required: true },
    gtype: { type: '"job" | "gang" | nil', description: '`job` para un trabajo, `gang` para una banda, `nil` para cualquier otro grupo.', required: true },
  }}
/>

<Tabs items={['TypeScript', 'Lua']}>
<Tab value="TypeScript">
```ts title="resource/server/index.ts"

```
</Tab>
<Tab value="Lua">
```lua title="server.lua"

  print(('user %d joined %s (%s)'):format(user_id, group, gtype or 'group'))

  print(('user %d left %s'):format(user_id, group))
```

<Callout type="info">
Las extensiones de vRP 2 y 3 reciben del puente sus propios eventos de extensión (`characterLoad`, `playerJoin`, `characterUnload`, `playerLeave`, `playerSpawn`, `playerDeath`, `playerMoneyUpdate`, `playerJoinGroup` / `playerLeaveGroup` y otros) a través del sistema de eventos de extensión de vRP, no como eventos de FiveM. No se disparan: `vRP:save`, `vRP:playerRejoin`, `vRPcli:playerSpawned`.
</Callout>

## Eventos de framework a los que responde ai-core

Los scripts escritos para un framework envían estos eventos esperando que el framework responda. ai-core responde en su lugar.

| Evento | Lado | Qué hace ai-core |
| --- | --- | --- |
| `QBCore:GetObject`, `esx:getSharedObject` | ambos | Llama al callback con el objeto core (`QBCore` / `ESX`). |
| `QBCore:Server:TriggerCallback`, `esx:triggerServerCallback` | servidor (desde los clientes) | Ejecuta el callback de framework registrado con `CreateCallback` / `RegisterServerCallback` y responde. Como mucho 30 peticiones por jugador en cualquier intervalo de 10 segundos. |
| `QBCore:Notify`, `esx:showNotification`, `esx:showAdvancedNotification`, `ESX:Notify` | cliente (desde el servidor) | Muestra la notificación de ai-lib. |
| `esx:showHelpNotification`, `ESX:TextUI`, `ESX:HideUI`, `qb-core:client:DrawText`, `qb-core:client:ChangeText`, `qb-core:client:HideText`, `qb-core:client:KeyPressed` | cliente | Muestra u oculta el aviso de ai-lib. |
| `qb-menu:client:openMenu`, `qb-menu:client:closeMenu` | cliente | Abre o cierra el menú de ai-lib con los elementos de qb-menu. |
| `progressbar:client:cancel` | cliente | Cancela la barra de progreso del puente. |
| `police:server:policeAlert` | servidor | Envía una alerta de policía al sistema de alertas activo en la posición del jugador. Los clientes envían `(text)` (una por jugador cada 10 segundos); los scripts de servidor lo disparan con `TriggerEvent` y `(text, camId, playerSource)`. |
| `qb-weathersync:client:DisableSync` / `EnableSync`, `cd_easytime:PauseSync`, `vSync:toggle` | cliente | Cuentan como motivos de pausa de la sincronización de clima y hora (consulta [Sincronización de clima y hora](/es/docs/developers/api/core-client/world)). |
