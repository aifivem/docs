У обновления две половины: установить новую версию ровно в том виде, в каком она поставляется, а затем перенести на неё собственные изменения сервера. Копировать старые файлы поверх новых нельзя никогда: так возвращаются старый код, старые ключи и старые ошибки, а новая версия ломается так, что причину трудно найти.

Эта страница написана для двух читателей: для вас и для ИИ-агента для программирования (Claude Code, Codex, Cursor...), которому вы её покажете. Оба следуют одной и той же процедуре.

## Попросите свой ИИ

Откройте папку данных сервера в своём агенте и вставьте этот текст, заполнив область:

```text
Обнови скрипты на этом сервере AI Core по https://aifivem.com/docs/update-a-script.md
Если в этой папке есть .claude/skills/aicore-script-update/, прочитай его SKILL.md и references: это та же процедура.

Область: <каждый устаревший скрипт ai-* и пакет | ai-inventory ai-garages | сторонние скрипты в C:\путь\к\новым-версиям>

- Сначала покажи мне список (имя, путь, текущая -> новая версия, заметки к релизу, требующие действий) и дождись моего согласия.
- Сделай резервную копию каждой папки, прежде чем её трогать, включая файлы, которые git игнорирует, например data/secrets.json.
- Возьми три дерева для каждого скрипта: старый upstream (версия, которая у меня работает, как она поставлялась), наше (папка сейчас), новый upstream.
  Сливай файл за файлом по этой трёхсторонней модели. Никогда не копируй старый файл поверх нового.
- Сохрани содержимое панели data/*.json, data/secrets.json, мои тексты локалей и мою базу данных.
  Никогда не выводи секрет в чат и никогда его не коммить.
- Никакого SQL без моего согласия и резервной копии затронутых таблиц. security.cfg никогда не ослабляется.
- Сгенерированные файлы (dist/, fxmanifest.lua, resource/server/tables.ts, data/schemas/) бери из новой версии
  и пересобирай build-ом; никогда не правь их вручную.
- Собери, сделай refresh, перезапусти и прочитай лог консоли на ошибки, а не только "Started resource".
- Не коммить и не пушь, пока я не попрошу.
- В конце дай отчёт по каждому скрипту на моём языке: смена версии, что изменилось в upstream, что ты перенёс
  и куда, что отпало (со старым значением), новые опции, оставленные по умолчанию, база данных, изменения cfg,
  результат build / перезапуска / лога, что проверить в игре и какие решения я должен принять.
```

<Callout>
В каждой папке сервера AI Core эта процедура есть как skill проекта в `.claude/skills/aicore-script-update/`: recipe txAdmin устанавливает его вместе с правилами, `tools/`, `docs/compat/`, `CLAUDE.md` и `AGENTS.md`, так же как ручная установка. Claude Code загружает его сам, когда вы говорите «обнови мои скрипты» или «вышла новая версия»; другие агенты находят его через `AGENTS.md`. На сервере, установленном более старым recipe, этих файлов может не быть: скачайте их из репозитория [aicore-server](https://github.com/aifivem/aicore-server) в папку сервера, как в разделе [Установка вручную](/ru/docs/installation#установка-вручную), сохранив свои cfg-файлы.
</Callout>

## Что остаётся вашим

| Что | Где | Что с этим делает обновление |
| --- | --- | --- |
| Настройки и содержимое панели | `data/*.json` в каждом скрипте | Сохраняются. Переводятся в новый формат, только если новая версия читает другие поля. |
| Секреты | `data/secrets.json` (git его игнорирует) | Восстанавливаются из резервной копии без изменений. Никогда не выводятся и не коммитятся. |
| Ваши тексты | `locales/*.json`, папка `locales/` или `languages/` стороннего скрипта | Ваши формулировки остаются для каждого ключа, который ещё есть; новые ключи добавляются на вашем языке; удалённые ключи уходят. |
| Ваши изменения кода | Любой исходный файл, который вы правили | Вписываются в код новой версии. Изменение, которому больше нет места, попадает в отчёт. |
| База данных | Ваши таблицы и строки | Никогда не удаляется. Новые таблицы и столбцы добавляются при старте; всё остальное ждёт вашего согласия. |
| Настройки безопасности | `security.cfg` | Никогда не ослабляются. Если релиз или поставщик этого требует, обновление останавливается и решаете вы. |

## Откуда берётся новая версия

| Скрипт | Новая версия | Что даёте вы |
| --- | --- | --- |
| Ресурсы `ai-*` в `resources/[ai]/` (включая ai-core, ai-lib и ai-mysql) | Релиз на GitHub репозитория, указанного в его `package.json` (`"repository": "github:aifivem/<name>"`) | Ничего |
| Пакеты `@aifivem/*` в `packages/` | npm (`npm view @aifivem/<pkg> version`) | Ничего |
| Любой другой ресурс (обычно в `resources/[standalone]/`) | Поставщик | Новую папку или zip |

ai-core проверяет каждый запущенный скрипт с репозиторием на GitHub (раз в 6 часов для каждого скрипта) и пишет в консоль `<name> <current> is outdated: <latest> is out (<url>)`; тот же список есть на дашборде админа. Проверки обновлений и пропускаемые скрипты настраиваются в [админ-панели](/ru/docs/admin-panel) во вкладке **General** (`updates.check`, `updates.ignore` в `data/settings.json` ai-core).

## Трёхсторонний перенос

Каждое обновление сравнивает три версии каждого файла:

- **Старый upstream**: версия, которая работает на сервере, в том виде, в каком она поставлялась.
- **Наше**: папка в текущем виде, включая незакоммиченные изменения.
- **Новый upstream**: новая версия в том виде, в каком она поставляется.

| Старый -> наше | Старый -> новый | Результат |
| --- | --- | --- |
| без изменений | изменён или без изменений | взять новый |
| изменён | без изменений | оставить наше |
| изменён | изменён | `git merge-file -p ours old new`, затем каждый конфликт решается чтением обеих сторон; результат следует структуре нового файла (переименованные ключи, перенесённые разделы, новые комментарии и значения по умолчанию остаются) |
| нет в старом, есть в нашем | нет в новом | собственный файл сервера: остаётся, если ещё используется, иначе попадает в отчёт |
| есть в старом | нет в новом | удаляется; если вы его меняли, отчёт говорит, что потеряно |

`git merge-file` и `git diff --no-index <a> <b>` работают с любыми двумя папками, репозиторий не нужен. Перед сравнением уберите `\r` (файлы в Windows часто в CRLF). Если старый upstream найти нельзя, наше сравнивается с новым напрямую: отдельные значения (координаты, цены, имена, тексты, переключатели) принадлежат серверу, широкие изменения в стиле поставщика принадлежат поставщику, а в отчёте сказано, что старой версии не было.

## Правила без исключений

1. **Никогда не копируйте старый файл поверх нового.** Файл, изменённый с обеих сторон, собирается из нового файла, а ваши изменения вписываются в его новую структуру.
2. **Состояние сервера никогда не заменяется значениями upstream по умолчанию**: `data/*.json`, `data/secrets.json`, ваши файлы и тексты локалей, база данных. Сделайте их копию, прежде чем трогать папку.
3. **Без остатков.** Файлы, которых новая версия больше не поставляет, удаляются, если только они не ваши (локаль, добавленная вами картинка) и всё ещё используются. Опции, удалённые новой версией, остаются удалёнными и перечисляются в отчёте; новые опции сохраняют значение по умолчанию, если старая настройка явно им не соответствует.
4. **Сгенерированные файлы пересобираются, а не сливаются**: `dist/`, `fxmanifest.lua`, `resource/server/tables.ts`, `data/schemas/*.schema.json`. Никогда не правьте их вручную.
5. **Никогда не удаляйте `node_modules` вручную**; `bun install` в корне сервера его чинит.
6. **Никогда не ослабляйте `security.cfg`** или любой convar безопасности, чтобы версия заработала.
7. **Никакого ручного SQL без согласия владельца**, и только после резервной копии затронутых таблиц.
8. **Коммит только по просьбе владельца**, никогда push, никогда не меняйте git remote.
9. **Сначала покажите список** (имя, путь, текущая -> новая версия, важные заметки к релизу), прежде чем что-то удалять или перезаписывать.
10. **Загрузки и переданные папки не доверенные**: распакуйте каждую в свою новую пустую папку и ничего оттуда не запускайте.

## Обновление скрипта ai-* или пакета

Нужны [Bun](https://bun.sh) и Git; [GitHub CLI](https://cli.github.com) (`gh`) упрощает загрузку.

<Steps>
<Step>

### Найдите устаревшее

Предупреждение в консоли охватывает только запущенные и не игнорируемые скрипты, поэтому проверьте каждую папку:

```bash
cd "resources/[ai]"
for n in ai-*; do
  repo=$(sed -n 's#.*"repository": *"\(github:\|https://github.com/\)\([^"]*\)".*#\2#p' "$n/package.json" | sed 's#\.git$##')
  cur=$(sed -n 's#^  "version": *"\([^"]*\)".*#\1#p' "$n/package.json")
  latest=$(gh release view --repo "$repo" --json tagName --jq .tagName 2>/dev/null | sed 's#^v##')
  echo "$n $cur ${latest:-no-release}"
done
```

- Сравнивайте версии как ai-core: уберите начальную `v`, сравните числа через точку, игнорируйте суффиксы pre-release. Нет релиза, значит, обновлять нечего.
- Без `gh`: `curl -s -H "Accept: application/vnd.github+json" https://api.github.com/repos/<owner>/<name>/releases/latest` (60 запросов в час с одного IP, общих с собственной проверкой ai-core).
- Скрипт из `updates.ignore` обновляется, только если владелец назвал его.
- Папка с версией выше последнего релиза или клон с коммитами после последнего тега не устарели: пропустите их, никогда не откатывайте папку назад.
- В `packages/` нет строки `repository`: сравните версию каждого `package.json` с npm. Сначала обновите пакеты, если новому релизу скрипта нужна версия, которой нет в локальных копиях.

</Step>
<Step>

### Прочитайте заметки к релизу и получите согласие

Прочитайте заметки каждой версии между текущей и последней (`gh release view <tag> --repo <repo> --json body,assets,url`): несовместимые изменения, нужные версии пакетов, миграции, новые строки cfg (`ensure`, `add_convar_permission`, ACE), новые имена `provide`, ручные шаги.

Покажите владельцу список и дождитесь согласия. Обновляйте в порядке зависимостей: пакеты, ai-mysql, ai-core, ai-lib, затем остальное.

</Step>
<Step>

### Скачайте старый и новый upstream

Для каждого скрипта две новые пустые папки вне сервера (например, `update/<name>/old` и `update/<name>/new`):

```bash
gh release download <tag> --repo <owner>/<name> --archive zip --dir update/<name>/new     # исходники тега
gh release download <tag> --repo <owner>/<name> --pattern '*.zip' --dir update/<name>/new # asset релиза, если он есть
unzip -q update/<name>/new/*.zip -d update/<name>/new/x
```

- Если у релиза есть asset, берите его; иначе исходники тега (в них есть закоммиченные `dist/` и `fxmanifest.lua`). Верхняя папка zip с исходниками называется `<owner>-<name>-<sha>/`.
- **Старый upstream** это тег версии, которая работает на сервере (стиль тегов видно через `gh release list --repo <owner>/<name>`). Его всегда можно скачать, поэтому у трёхстороннего сравнения всегда есть база.
- Ничего в этих папках не запускается, не устанавливается и не собирается.

</Step>
<Step>

### Сделайте резервную копию

- Скопируйте всю папку скрипта, кроме `node_modules`, в `update/<name>/ours` (в Windows `robocopy "<src>" "<dst>" /E /XD node_modules`; коды выхода robocopy меньше 8 означают успех). Это «наше» для слияния и путь назад.
- Файлы, которые git игнорирует, есть только в этой копии: `data/secrets.json`, `data/*.json.bak`. В клоне git их перечисляет `git ls-files --others --ignored --exclude-standard`.
- Незакоммиченные изменения в клоне (`git status --porcelain`) тоже изменения сервера. Скажите о них владельцу; коммитьте их только по его просьбе.

</Step>
<Step>

### Сливайте файл за файлом

Примените трёхстороннюю модель к старому, нашему и новому и запишите результат в папку скрипта:

| Файл | Правило |
| --- | --- |
| `resource/**`, `web/src/**`, `bridge/**`, `sql/**`, Lua и другие исходники | Три стороны. Локальное изменение, чей код переехал или чей контракт изменился, подгоняется под новый код; изменение без места попадает в отчёт. |
| `package.json` | Новый upstream плюс локальные добавления, которые ещё имеют смысл. `version` заканчивается на версии нового релиза, иначе проверка обновлений продолжит предупреждать. |
| `dist/`, `fxmanifest.lua`, `resource/server/tables.ts`, `data/schemas/*.schema.json` | Взять новые; build пересоздаёт их. |
| `data/<file>.json` (содержимое панели) | Оставить наше (см. ниже). |
| `data/secrets.json`, `data/*.json.bak` | Восстановить из резервной копии без изменений. |
| `locales/en.json` | Три стороны: новые ключи и плейсхолдеры из upstream, формулировки сервера для ключей, которые ещё есть. |
| `locales/<lang>.json`, которого нет в релизе | Оставить. Добавить новые ключи в переводе на этот язык в том же тоне, убрать удалённые ключи, следовать изменённым плейсхолдерам (`{0}`, `{1}`). |
| `CLAUDE.md`, документация | Взять новые, вернуть собственные заметки сервера. |

**Содержимое панели (`data/*.json`)** это живое содержимое сервера, изменяемое в панели; релиз приносит только значения по умолчанию.

- Та же схема (новый `schema.ts` или loader читает те же поля): оставьте наше как есть. Файл, который добавляет новая версия: возьмите поставляемый.
- Схема изменилась: найдите собственную миграцию скрипта при старте (заметки к релизу, миграция, вызываемая при старте). Если она есть, оставьте наше на месте; она преобразует его при старте. Если нет, преобразуйте вручную по новому loader и схеме: те же имена полей, типы и формат id, что в поставляемом файле, каждое значение сохранено, новые поля со значением по умолчанию из поставки, удалённые поля убраны и указаны в отчёте. Проверьте, что каждый файл парсится.

**База данных.** Каждый скрипт создаёт свои таблицы из `sql/main.sql` при старте: создаёт недостающие таблицы и добавляет недостающие столбцы, но никогда не удаляет, не переименовывает и не меняет столбец и не добавляет ключи. Сравните старый и новый `sql/main.sql`:

- Новые таблицы и столбцы: их применит перезапуск.
- Изменённый тип столбца, новый индекс или ключ, переименованный или удалённый столбец: релиз должен принести свою миграцию (заметки к релизу, серверный код), она выполняется при старте; проверьте лог. Если её нет, напишите SQL, покажите владельцу, сделайте копию затронутых таблиц и выполните его только с его согласия.

**Cfg-файлы вне папки.**

- `server.cfg`: новый скрипт получает свою строку `ensure` в порядке зависимостей; удалённый её теряет (сначала спросите).
- `env.cfg` и `env.example.cfg`: скрипту, который начинает использовать базу данных, нужен `add_convar_permission <resource> read mysql_connection_string`.
- `permission.cfg`: строки ACE, которых требуют заметки к релизу.
- `security.cfg`: никогда не ослабляется.

</Step>
<Step>

### Соберите, перезапустите, проверьте

1. `bun install` в корне сервера, если изменился какой-либо `package.json`.
2. В каждом обновлённом скрипте: `bun run typecheck`, `bun run lint`, `bun run build` (или `bun tools/run.ts build ai-x ai-y` из корня сервера). Собирайте всегда: `dist/` должен получаться из слитых исходников. Исправляйте ошибки в перенесённых изменениях сервера; ошибка в нетронутом коде upstream попадает в отчёт, а не латается.
3. Сравните результат с новым upstream: `diff -r --strip-trailing-cr -x node_modules -x dist -x data update/<name>/new/x/<top> "<script folder>"`. Каждое оставшееся различие должно быть одним из изменений сервера.
4. Сделайте refresh и перезапуск:

   ```bash
   bun tools/rcon.ts --log ../default/logs/fxserver.log --wait 3 "refresh"
   bun tools/restart.ts --from ai-inventory   # один скрипт
   bun tools/restart.ts                       # после обновления ai-core, ai-lib, ai-mysql или пакетов
   ```

   `bun tools/restart.ts` перезапускает ai-core, делает `ensure` для каждого `ai-*` после него и проверяет, что каждый запустился. Сторонние скрипты, зависящие от ai-mysql, останавливаются вместе с ним: снова сделайте им `ensure` по имени. Новая строка `provide` требует полного запуска сервера: `bun tools/rcon.ts "quit \"<reason>\""`.

5. Прочитайте лог консоли на `SCRIPT ERROR`, `Failed to load script`, `[client error]`, ошибки загрузки или проверки панели и ошибки базы данных, а не только `Started resource`. Предупреждение `is outdated` должно пропасть после следующей проверки скрипта.

</Step>
</Steps>

## Обновление стороннего скрипта

Новую версию даёт владелец (папку или zip). Установите её как есть, перенесите на неё изменения сервера, затем проверьте, что ai-core по-прежнему правильно с ней общается.

<Steps>
<Step>

### Сопоставьте поставку с установленным

- Каждая папка верхнего уровня с `fxmanifest.lua` (или `__resource.lua`) это ресурс; папка `[category]` содержит несколько. Распакуйте zip в новую пустую папку и ничего оттуда не запускайте.
- Найдите установленную копию по имени папки внутри `resources/` (например, `find resources -maxdepth 3 -type d -name <name>`). Сохраняйте установленное расположение, а не категорию из поставки. Нет совпадений или их несколько: спросите владельца. Ещё не установленный скрипт устанавливается, только если так скажет владелец.
- Папка `ai-*` в поставке идёт не по этому пути: скрипты `ai-*` обновляются с GitHub (выше). Спросите владельца, что это за папка.
- Прочитайте оба манифеста: `version`, `files`, скрипты, `dependencies`, `provide`, `escrow_ignore`, `ai_replaces`. Версия, которая уменьшилась, или поставка без файлов, которые есть в установленной копии, может оказаться более старой сборкой: сравните и сообщите вместо установки.
- Новые зависимости: oxmysql обслуживает ai-mysql (никогда не ставьте oxmysql рядом); ox_lib и другие библиотеки устанавливает владелец; зависимость от того, что заменяет ai-core (`es_extended`, `qb-core`, `qbx_core`, `pma-voice`, `ox_inventory`...), уже выполнена.
- Покажите сопоставленный список (имя, путь, текущая -> новая версия) и дождитесь согласия.

</Step>
<Step>

### Сделайте резервную копию

- Скопируйте всю установленную папку в папку резервной копии вне сервера (`robocopy "<src>" "<dst>" /E`). Для папки, которую не отслеживает ни один репозиторий git, эта копия единственная копия версии сервера.
- Если git отслеживает папку: `git status --porcelain -- <path>` показывает незакоммиченные изменения (они считаются нашими; скажите владельцу), а `git ls-files --others --ignored --exclude-standard -- <path>` показывает рабочие файлы, которые git игнорирует (сохранённый JSON, кэши), они есть в копии.

</Step>
<Step>

### Найдите изменения сервера

Получите старый upstream в таком порядке:

1. У владельца ещё есть старый zip или папка от поставщика.
2. Скрипт с открытым кодом на GitHub: релиз или тег установленной версии.
3. История git, если папка отслеживается: коммит, который выставил установленную `version` (`git log -S"version '<old>'" -- <path>/fxmanifest.lua`). Если этот коммит заодно заново применил прежние настройки, его config-файлы считаются нашими, а чистая поставка находится на коммит раньше.
4. Ничего из этого: сравните наше с новой версией напрямую и укажите это в отчёте.

Затем прочитайте каждое различие старый -> наше (правки сервера: конфиги, `locales/*` или `languages/*`, editable-файлы, `data/*.json`, `fxmanifest.lua`, SQL, изображения, звуки, stream-файлы, патчи кода) и старый -> новый (изменения поставщика: добавленные и удалённые файлы, переименованные ключи, перенесённые разделы, изменённые editable-функции). В скрипте с escrow (есть `.fxap`) читать и править можно только файлы из `escrow_ignore`; правку в файле, который новая версия закрыла escrow, перенести нельзя, она попадает в отчёт.

</Step>
<Step>

### Установите новую версию

Полностью удалите установленную папку, затем скопируйте новую папку по тому же пути, включая скрытые файлы (`.fxap`). Старые остатки это ошибки; старая версия остаётся в резервной копии. Возвращайте рабочие файлы из копии, только если новая версия использует их в том же формате; иначе преобразуйте или отбросьте их и сообщите.

</Step>
<Step>

### Перенесите изменения сервера

Для каждой правки найдите, где эта настройка находится в новой версии, и впишите туда значение в новом формате:

- **Тот же ключ, тот же файл:** задайте значение в новом файле; сохраните его комментарии и разметку.
- **Переименованный или перенесённый ключ:** найдите новый ключ, читая код, который его использует (ищите старое имя, его комментарий, значение по умолчанию, текстовый ключ), и преобразуйте значение в новую форму.
- **Конфиг перенесён в файл данных** (JSON, который правит собственная панель скрипта): прочитайте новый loader и поставляемый файл, впишите старые значения ровно в эту схему (имена полей, типы, формат id, отступы) и проверьте, что он парсится. Не полагайтесь на конвертер, который скрипт может запустить.
- **Существующие файлы данных сервера:** перенесите их, преобразуйте поле за полем, если схема изменилась, никогда не заменяйте их примером поставщика.
- **Удалённая опция:** её больше не читает никакой код (поиск это подтверждает): уберите её и укажите в отчёте со старым значением.
- **Editable-файлы** (`client/editable.lua`, `server/editable.lua`...): начните с нового файла и заново примените каждое изменённое тело функции, подогнав его к изменённой сигнатуре или возвращаемому значению; новые функции остаются по умолчанию.
- **Языки:** сохраните формулировки сервера для каждого ключа, который ещё есть; добавьте новые ключи в каждый языковой файл, который использует сервер, в переводе в тоне существующих текстов; уберите удалённые ключи; следуйте изменённым плейсхолдерам.
- **fxmanifest:** новый, плюс только те собственные добавления сервера, которые ещё имеют смысл. Никогда не меняйте `version`.
- **SQL** (`*.sql`, папки установки): сравните старый и новый; новые таблицы, столбцы и индексы попадают в отчёт как SQL, который запускает владелец. Без его согласия ничего не выполняется.
- **Учётные данные** (токены ботов, ключи API, адреса вебхуков в конфигах): никогда не выводите их. Перенесите их из копии; если это невозможно, оставьте новое значение по умолчанию и укажите владельцу файл и ключ.
- **Ассеты** (`stream/`, изображения, звуки): поставщика плюс файлы, добавленные сервером и всё ещё используемые.
- Координаты, предметы, цены, тексты и поведение переносятся в точности; кроме собственных правок сервера ничего не меняется.

</Step>
<Step>

### Проверьте совместимость с ai-core

Скрипт может быть одним из тех, с кем общается ai-core. Найдите каждое место, где он упоминается:

```bash
grep -rln "<name>" "resources/[ai]/ai-core/resource" "resources/[ai]/ai-core/bridge" docs/compat
```

| Категория | Адаптеры ai-core | Заметка |
| --- | --- | --- |
| Инвентарь | `resource/server/inventory/adapters/`, `resource/client/inventory/adapters/` | `docs/compat/inventory.md` |
| Ключи от машин | `resource/server/vehicleKeys/adapters/`, `resource/client/vehicleKeys/adapters/` | `docs/compat/vehicle-keys.md` |
| Телефон | `resource/server/phone/adapters/` | `docs/compat/phone.md` |
| Вызовы полиции | `resource/server/dispatch/adapters/` | `docs/compat/dispatch.md` |
| Радиальное меню | `resource/client/radial/adapters/` | `docs/compat/radial.md` |
| Эмоции, руки вверх | `resource/client/gestures.ts` | `docs/compat/gestures.md` |
| Время и погода | `resource/server/world.ts`, `resource/client/world.ts` | `docs/compat/weather.md` |
| HUD | `resource/client/hud.ts` | |
| Голос, чат | ai-voice (API pma-voice), ai-chat (API `chat`) | `docs/compat/voice.md`, `docs/compat/chat.md` |
| Использование ESX / QB / Qbox | `bridge/` | `docs/compat/bridge.md`, `docs/compat/frameworks.md` |

- Для каждого export, event и callback, которые использует адаптер, проверьте новую версию: всё ещё есть, те же аргументы, та же форма результата, тот же момент вызова. В коде с escrow проверьте читаемые файлы и документацию поставщика и перечислите то, что проверить нельзя.
- Несовпадение исправляется только в файле адаптера (тонкий перевод), с повышением его проверенной версии; затем typecheck, lint и build ai-core и его перезапуск (`bun tools/restart.ts`).
- Новая строка `ai_replaces` или `provide` может заставить ai-core отклонять подключения, пока ещё работает заменитель `ai-*` (см. [Замена скрипта ai-*](/ru/docs/compatibility#замена-скрипта-ai-)): назовите папку, которую владелец должен удалить.
- Обновите `docs/compat/<script>.md` (проверенная версия, статус, точный конфиг или патч, известные ограничения); поддерживаемый скрипт без заметки получает её.

</Step>
<Step>

### Проверьте и перезапустите

- Сравните установленный результат с новой версией: каждое различие это изменение сервера, и не осталось ни одного старого файла, которого нет в новой версии (кроме восстановленных рабочих файлов).
- Изменённый Lua парсится, JSON парсится, каждый заданный ключ конфига существует в новом коде.
- Если никакой SQL не ждёт владельца: `bun tools/rcon.ts --log ../default/logs/fxserver.log --wait 3 "refresh"`, затем то же с `"ensure <name>"`, и прочитайте лог на `SCRIPT ERROR`, `Failed to load script` и собственные ошибки скрипта. Зависящие от него скрипты, которые остановились, запускаются снова.

</Step>
</Steps>

## Итоговый отчёт

Обновление заканчивается отчётом на языке владельца, по разделу на каждый скрипт:

- имя, путь, текущая -> новая версия, источник (тег релиза или папка владельца)
- что изменилось в upstream и важно для этого сервера
- перенесено: изменения кода, тексты и настройки, и куда каждое попало в новой версии
- оставлено как есть: `data/*.json`, `data/secrets.json`, собственные файлы локалей; выполненные преобразования схемы (миграцией скрипта или вручную)
- отброшено или не перенесено: удалённые опции и правки без места, со старым значением, чтобы владелец мог решить
- новые опции, оставленные по умолчанию, которые владелец может захотеть задать
- база данных: таблицы или столбцы, добавленные при старте, миграции, выполненные релизом, SQL, ждущий владельца
- нужные или сделанные изменения cfg (строки `ensure` в `server.cfg`, права convar в `env.cfg`, `permission.cfg`)
- совместимость: проверенные или изменённые адаптеры и заметки `docs/compat` (сторонние скрипты)
- результат build, перезапуска и лога и что проверить в игре

В конце перечислены решения, которые должен принять владелец. См. также [Работа с ИИ](/ru/docs/working-with-ai).
